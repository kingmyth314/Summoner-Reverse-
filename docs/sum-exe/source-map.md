# Source-file map
{: .no_toc }

1. TOC
{:toc}

**Summary:** Sum.exe's code falls into three blocks, in link order: Summoner's own game
code, then Volition's shared `vsdk` engine, then the Visual C++ 6 C runtime. Each original
`.cpp` file's functions sit together, so the address of any function tells us roughly which
module it belongs to.

Generated by `node tools/tu-map.mjs` (2026-10-12). It finds source-path strings
(`D:\projects\Summoner\pccode\...`) and the `PUSH imm32` / `MOV r32, imm32` instructions in
`.text` that reference them: 61 path strings, 35 files referenced.

## Layout

| Address range (approx.) | Block | Evidence |
|---|---|---|
| `0x401000`-`0x500a2f` | Summoner game code: `summoner\`, `engine\`, `levelscripts\` | Every game-side source reference falls in this range (**observed**) |
| `0x500a30`-`~0x569fff` | Volition `vsdk` engine library | First `vsdk` code: the mouse module at `0x500a30` (its static initialisers); first `vsdk` path reference `0x501d92` (`bmpman`); `FrameDone` (`0x501510`) sits just before it; last vsdk reference `0x555519` (**observed**). The end of the block is *inferred* |
| `~0x56a000`-`0x57dfff` | MSVC 6 C runtime (static) | `__ftol` (`0x56c7e4`), `exit` (`0x56da99`) and Ghidra-identified CRT names (*inferred* boundary) |

Known functions agree with this layout:

- `os_registry_*` at `0x512050`-`0x512370`, next to the `registry.cpp` reference at `0x512037`;
- the allocator call at `0x5124f2`, inside `memory.cpp` (`0x512516`-`0x512852`);
- the functions tagged `gr_opengl.cpp` at `0x54d5c0`-`0x550640` (`gl_convert_a8_to_rgba8888` to `clamp_ubyte`), around the
  `gr_opengl.cpp` references at `0x54f70c`-`0x54f725`.

    `multiendgame.cpp`
  - `new_multi`, `new_multichat`, `new_gamecreate`, `new_gamelist`, `new_int_multi_update`
  - `new_pxochat`, `new_pxo_banner`: PXO is Parallax Online, Interplay's matchmaking
    service.
- **Level scripts:** `level_scripts.cpp`, `level_scripts_common.cpp` and one
  `level_script_<level>.cpp` per scripted level (catacombs, courtyard, eleh, ikaemos, iona,

The multiplayer files explain the [network layer](vsdk-os.md#networking-0x517590-0x5194ab):
PC Summoner was built with a multiplayer mode (chat, trading, saved multiplayer games,
PXO lobby). It was not offered in the retail game, but much of its code is still in
Sum.exe.

Because strings are numbered in file order, the id ranges also show the order of these
files. That can help assign functions to files later: a function that uses string 47 belongs
to the file whose section contains 47.

## Translation units from data locality

`node tools/tu-split.mjs` (2026-10-14) proposes a boundary for every source file, not just those that reference a
path string. It rests on three observations (all **observed** in this binary):

1. **The static initialiser table is in address order.** All 652 entries of the table at `0x588004` point to
   increasing addresses, so the table gives the link order. Each file's initialisers sit inside its own code,
   usually at the start. Example: `init_realtimetimer_5b28bc` (`0x4011c0`) comes just before the first
   `new_assess.cpp` function.
2. **Initialised data follows link order almost perfectly.** For globals used by a single function, 96-99% of
   address-adjacent pairs belong to nearby functions. That is true inside a file as well as between files, so it
   orders the code but does not show where one file ends.
3. **Each file's `.bss` is one contiguous block, in declaration order.** The functions of one file use `.bss`
   addresses that interleave. The next file's block starts above. Example: `new_assess.cpp` uses
   `0x5b27fc`-`0x5b28d4` and `new_automap.cpp` uses `0x5b29e0`-`0x5b2d08`.

The tool:
1. Treats a global as private when all its users lie within 60 functions of each other. Entries of
   `localize_strings` never count.
2. Allows a cut only where no private global is used on both sides, and never between an initialiser thunk and
   its initialiser.
3. Forces a cut between two functions tagged with different `.cpp` files.
4. Joins the pieces greedily. A new unit starts when the next piece's `.bss` lies more than `0x40` bytes above the
   unit's. The gap lets a file whose statics are declared in function order (`ui_parse_button`,
   `ui_parse_checkbox`, ...) stay in one unit.

**Result (2026-10-15):** 99 units over `0x401000`-`0x56a000`. None mixes two `.cpp` tags, and only 1 of the 65
tagged files is split. Getting there took about 80 module-tag corrections, each checked against the neighbouring functions
and the data they use:
- the three `*_render_character_mesh` functions go to `vsdk\ca`;
- header inlines (`gr__Mode` accessors, `Mempool` methods) get folder-level tags (`vsdk\gr`, `vsdk\os`);
- 14 tags spelled `memory.cpp` are `vsdk\os\memory.cpp`;
- the 16 Direct3D texture-cache functions after the Glide code get `vsdk\gr\directx`;
- stray game tags that sat in another file's code were cleared (`-`).

The one split file was `vsdk\gr\gr.cpp` (`0x505550`-`0x5081cf`). It is a single object: 30 `gr::Mode`
initialisers, `init_gr_screen` and four console commands (initialiser table `0x5887ec`-`0x588874`), then the
functions from `gr_init` (`0x505e00`) on, then three out-of-line header inlines (`0x508160`-`0x5081cf`). The
`.bss` rule cut it because the mode objects' `.bss` addresses follow the initialiser order, not the source order,
so the unit's `.bss` (`0x25d88a0`-`0x25d9237`) is not filled in function order. 26 module tags of its own data
(render-mode objects tagged with the files that use them, the fog fields, three flags and three console
commands) were corrected on 2026-10-15. *Known limit:* with fewer forced cuts, two untagged blocks merge into their neighbours: the
interface code between `new_hud.cpp` and `new_inventory.cpp`, and the party-inventory block after `objects.cpp`.
`--score` lists any remaining "stray?" tags for review.

### Version 2: boundaries from the binary alone (2026-10-15)

`node tools/tu-split2.mjs` (written by an agent, reviewed) finds file boundaries without needing module tags. Tags
only constrain the result, and `--blind` ignores them so the method can be measured.

1. **A graph of functions.** Edges join consecutive users of a private global (`.rdata`, `.data` and `.bss`), calls
   within 60 functions, data-order inversions, and a static initialiser with the first later function that uses its
   object. A `cmp reg, imm` against a data address is a loop bound one past an array; it counts as the array's last
   byte, not as a use of the next file's first global.
2. **Static-init groups.** Each of the 652 initialiser-table entries, with its jmp target, atexit registration and
   destructor, forms a group. A group is never cut, and a cut where a run of groups starts gets a bonus: every file
   with dynamic initialisers has them in front.
3. **Code style.** Most files are compiled with optimisation (no frame pointer, `0x90` padding). A few,
   `living_entity.cpp`, `objects.cpp` and the cutscene code after `gameplay.cpp`, were compiled **without**
   optimisation: every function opens an `ebp` frame and functions are padded with `0xcc` (**observed**). Such a run
   is one file, with exact ends.
4. **Dynamic programming** picks the cuts that maximise a modularity-style score.

Measured on the 64 transitions between the 65 reviewed `.cpp` tags (the tag set before the 450 unit-derived tags
were added):

| | Blind recall | Blind precision | Hide-one-file recall |
|---|---|---|---|
| `tu-split.mjs` | 2/64 (3%) | 2/2 | 79/128 (62%) |
| `tu-split2.mjs` | **63/64 (98%)** | **96%** (8 cuts inside files) | **126/128 (98%)** |

Strings, COMDAT filtering and code alignment added nothing. With the current tags it gives 210 units and no split
file. **Remaining failures:** `skeleton.cpp` / `stringpool.cpp` is not separated, a file's console-command tail can
merge into the next file's initialisers, and the party-inventory block merges into `item_paging.cpp`.

**Tagging from the units (2026-10-15).** Each `tu-split2` unit that holds exactly one file's tags passed that file
to its untagged functions (an agent proposed, I validated). Units with no tag got a file name only from evidence.
The game's `strings.tbl` groups its strings under comments like `// level_script_courtyard.cpp`, so a function that
uses a string id from that block belongs to that file. This added 35 more file names: `ai.cpp`, `combat.cpp`,
`summoner.cpp`, `spells.cpp`, `multitrade.cpp`, `new_tutorial.cpp`, `new_multichat.cpp` and 19
`level_script_*.cpp` files, among others. **State:** 102 files are tagged and none is split. About 3,100 functions
have a file, 1,760 only a folder, and 3,780 neither (mostly the C runtime, unwind funclets, header inlines and the
engine units no evidence names). Against the 101 transitions of this larger tag set, the blind splitter finds 91.

### Units without a file name (2026-10-15)

For 40 units no source path or reference names the file. They are labelled by what their functions do (from the
names and the strings they use; *inferred*). Many still hold several files that the splitter merges, for example
bosses, `level_scripts_common.cpp` and the savegame code in one unit. These are the next places to cut by hand.

**Round 3 (2026-10-15).** A third pass gave 369 untagged functions a file and corrected 11 tags. Each file is
backed by a `strings.tbl` `// file.cpp` block that its functions read, or by a path string whose uses bracket the
functions. The unit it forms was checked with `tu-split2.mjs` at gamma 10, 30 and 80.
- New files from `strings.tbl`: `level_scripts.cpp` (59 functions, `0x4d4bc0`-`0x4d6600`, ids 469-476),
  `conversationctl.cpp` (31, from the controller object's static initialiser to id 468), `multichat.cpp` (13, ids
  218-222), `multicontainer.cpp` (13, ids 223-224) and `multiplayerdata.cpp` (10).
- `multisave.cpp` (`0x46cc60`-`0x46da80`): the multiplayer `.plr` files and the 300 s autosave.
  `mp_player_file_write` reads id 237, "No description", from the `// multisave.cpp` block. These 10 functions
  had been put in `item_paging.cpp` by unit propagation; that file's path string is at `0x46cc2c`, before the
  range. Id 237 is also read by `saveload_scan_saves`, so a string id does not prove a file on its own.

- The `timer.cpp` tag on `timer_wait` (`0x530bf0`) was wrong. The function sits between two os functions, so it is
  now `vsdk\os`.

The tagged set is now 111 files and 4,466 functions. The blind score, which hides each tagged file in turn, falls
to 85.6% recall and 91.3% precision. Most misses are files that sit next to each other with no gap between them:
the per-level scripts, `plainstring.cpp` into `parse.cpp`, `norlsallocpool.cpp` into `timer.cpp`.

## Notes for later

- Link order within `vsdk` is not alphabetical. For example, `os\registry` and `os\memory`
  are at `0x512xxx`, `os\cmdline` at `0x53e3ab` and `os\stringpool` at `0x544c81`. It
  probably follows the original project's file order. A future matching build must link
  objects in the same order.
- `levelrender.cpp` (`0x48e4d9`-`0x4914c6`; its code starts at `0x48db30`) and `living_entity.cpp`
  (`0x4569a3`-`0x461bcd`) span large ranges, which hints at their size. The `levelrender_*` functions at
  `0x481680`-`0x48743f` (static initialiser entries 239-249, the console commands lod_dist to Cull_ground_too)
  are a separate unit before `multichat.cpp`, written as `src/decomp/game/unnamed_render_scene_0x481680.cpp`;
  the shadow table (`0x487440`-`0x48789f`) and the equip packets (`0x4878a0`-`0x487b8f`) follow it, and the
  containers, experience table, effect objects and PXO user tracker (`0x489730`-`0x48db2f`) sit between
  `multicontainer.cpp` and `levelrender.cpp` (placeholder files, D4304, D4400).
- Next refinement: once the Ghidra function list is available (`symbols/ghidra-functions.tsv`),
  assign every function to the nearest bracketing file references.
